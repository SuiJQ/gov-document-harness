`档位: object` 同理：档位值无类型约束，非法档位要到 `TIER_BY_ID[...]` 才 KeyError。

## #4 的误判是怎么来的

第一轮我写「投影层根本没有 `artifacts`」，依据是一条

```
grep -rn "artifacts" src/ --include=*.py | head -8
```

**`| head -8` 截断了输出**，只看到 `fakes.py` 与 `state_codec.py`，
没看到 `projection.py:133` 的

```python
artifacts: tuple[tuple[str, str], ...] = ()
```

于是我据此断言「`_最终正文()` 恒返回空串」，还把它列为最高危写进报告。

**实际**：`artifacts` 存在，并由 `ARTIFACT_READY` 在 `projection.py:162` 填充。
`getattr(投影, "artifacts", ())` **取得到值，函数正常工作**。
界面另有 569、641 两处**本来就是直接属性访问**，只有 651 那处用了 `getattr`。

这条误判的性质比原缺陷更值得记：**用被截断的输出当全量事实**，
且据此升级了风险级别（把「防御性写法」说成「现在就坏」）。

## #4 真正的缺口（仍然存在，只是不同）

`Projection` 协议**只声明 `accept` / `lines` 两个方法**，结构化字段一个都没声明，
而界面要读它们。后果：

1. 界面读 `.artifacts` 过不了类型检查，只能 `getattr` 兜底——
   兜底的名字写错会静默取默认值（本轮证伪实验证明：行为判据此时**不红**）；
2. `DebugProjection` 早期缺这 7 个字段，`--debug` 一跑就 `AttributeError`——
   当时的修法是改继承，**根因（协议不约束字段）没动**。

所以修复不是「补一个字段」，而是**给协议补齐 7 个字段声明**，
让「界面读投影字段」这条路重新受类型检查保护。

## 改类型后**立刻暴露**的两处真实缺口

这正是本轮最值得记的一点：**`object` 标注不掩盖运行时错误，它掩盖编译期检查**。

1. `结果.error.detail` —— `Result.error` 类型是 `AppError | None`，
   `is_error` 是普通 property 不做窄化，标真类型后立刻报
   「`detail` 不是 `None` 的属性」。此前被 `object` + `ignore` 盖住。
2. 两个替身缺成员（`_假编排` 的返回值没有 `error`、`_失败的编排` 没有 `事件`）——
   此前靠 `getattr` 兜底「通过」。**替身不完整被兜底遮住，
   和接线不完整被兜底遮住是同一个病**：两端都在缺东西，判据却全绿。

**结论**：两类判据不可互相替代。行为判据只抓「已经坏了」，
抓不到「还没坏但埋了雷」——兜底写法在字段名正确时行为完全正常，
只有源码判据能拦住它。两者都要留。

## 判据自身的三次修正

写判据的过程里，判据自己错了三次，都由全量测试当场暴露：

1. 源码判据扫全文 → **把本仓文档字符串里写的「原先挂的是 `pyright: ignore`」
   当成了违规代码**，判据把自己判红。改用 `tokenize` 剔除 `COMMENT` 与 `STRING`。
2. 类型忽略本身就是注释，`tokenize` 会剔除它——故那条判据反过来做：
   用 `ast` 找出**文档字符串所在行**并排除，余下行的注释才算数。
3. 「实现字段不得多于协议」这条方向错了：`DebugProjection` 的
   `prefix`/`records` 是**正当的子类扩展**（只经 `lines()` 暴露，刻意不给界面读）。
   改为只对基类 `StandardProjection` 做双向严格检查。

## 补了什么

### `error.raised`（第 1 批）

### `artifact.published`（第 1 批）

**问题**：落盘这件事在 journal 里**没有任何痕迹**，只有 `export.done`
携一份文件名列表。架构 §5.4 点名要防的「界面显示的和落盘的不是一份」，
**事后无从对照**。

**修**：改端口。`ExportPort` 返回值由 `tuple[str, ...]` 改为
`tuple[落盘摘要, ...]`（`文件名` / `种类` / `hash`）。

**hash 必须由写入侧算**：编排层拿的是 `内容: str`，落盘走 `编码`
（用户可配 `gb18030`）。同一串字符按 UTF-8 与 GB18030 写出的字节完全不同，
hash 也完全不同。编排在旁边重算等于假设「编码没变」——而那正是要防的假设。

**顺带修一个隐患**：`write_text` 走文本模式，`newline=None` 时
**会做换行转换**（Linux 写 `\n`、Windows 写 `\r\n`）。
于是 hash 在 Windows 上复算不出来，而「能用 `sha256(路径.read_bytes())`
复算」正是该 hash 的用途。改 `write_bytes` 后字节只由编码决定，跨平台可复算。
GB18030 行为经既有判据（`test_export_wiring.py`）确认未变。

# 修复（第 4 批续：run.resumed 与 user.answered）

## `run.resumed`

**问题**：续跑在 journal 里**没有任何痕迹**——只有一条 `run.started`。
于是事后无从区分「一次跑完」与「跑了三次接起来」。
而排查「为什么这次这么快」「这次模型只调了两次」时，
最该看的恰恰是续跑账（`state.json` 的 `completed_call_ids`）。

**修**：把 `已完成调用` 提成局部变量（原先内联在 `_过程(...)` 的实参里），
判据是**它非空**——那些调用已被幂等记账跳过，正是一次续跑的确凿证据。
空则不发：每次都发的话它就成了噪声，而噪声的代价很实在
（journal 里到处都是 `run.resumed`，真出现一次续跑时反而看不见）。

判据还守着**顺序**：先 `run.started` 再 `run.resumed`。

## `user.answered`

**问题**：事件流里只有 `user.question_raised`（工具层发），
**答复侧零留痕**。journal 无法回答「这次提问到底有没有得到答复」，
而「没答复」和「卡住了」的现场症状都是**程序停住不动**，排障只能靠猜。

**修**：`flow_ask_user` 拿到答复后经 `工具依赖.记事件` 发一条。

**只记字段码，不记答案全文**（D-030）——答案可能含用户不愿外传的实质。
判据专门用一段密文验证它没进载荷，将来有人「顺手把答案带上方便排查」
就会当场变红。

载荷里**没有「拒答」字段**：闸门超时/界面崩时 `问用户` **抛异常**，
那条路径到不了这里。「没拿到」由 journal 里 `question_raised` 后无
`answered` 本身表达——**闭环缺口就是信号**，不需要另设字段。

另两条判据守着两条容易踩的接线坑：
- 未接线的提问**不得**发 `answered`（否则出现无提问的答复假痕迹）
- 没挂 `记事件` 时提问**仍须成功**（留痕不得拖垮主流程，
  这正是 D-266「插话转达恒为 None」那类接线风险）
