# 三轮实测方案（用户裁定 · 2026-10-06）

> 用户原话的完整理解版本。**每条都是裁定，不是建议。**

## 统一理解

**跑三次：咨询、Flash、Pro。每次模型完美表现、不制造任何意外。同时从四个视角观察，两个轴比对。所有差异都算在 Harness 头上。**

- **完美模型 = 归因手段**。把模型从变量里摘出去，剩下的异常就没有推诿余地。
- **全面比对 = 发现手段**。摘干净变量是为了让异常可归因，不是为了少查。
- **不造错，不等于不比对。**

## 两个轴

| 轴 | 比什么 | 例子 |
|---|---|---|
| **A：视角 ↔ 视角** | 同一件事在不同视角是否一致 | 「这边显示已经完成，那边却还在转」 |
| **B：预期 ↔ 实际** | 模型拿到的是不是它应得的 | 「模型拿到的是个缺少的信息，它没有拿到它应得的内容包」 |

两者都要做，缺一不可。

**A 轴不需要事前准备**——矛盾本身就是证据。
**B 轴必须事前写下预期**——否则事后总能说「那是因为它不需要」。**预期只能事前写，跑完不许改。**

## 四个视角

| 视角 | 看什么 |
|---|---|
| 开发者 | 日志、系统运行状态 |
| TUI 用户 | 界面是否正常 |
| 被请求的模型 | 通过假端点看它实际收到了什么 |
| 产物 | 最终成果 |

产物视角保留——它是唯一能抓到「日志绿、界面漂亮、退出码 0、但稿子是空的」那类静默坏结果的地方。

## 执行规则

1. **顺序固定**：咨询 → Flash → Pro，失败即停。咨询通不了，后面两轮都是同一根因的噪音。
2. **三档本身就是实验设计**：咨询 1 人 → Flash 3 人 → Pro 5 人，逐档加角色。失败能定位到人——Pro 挂了 Flash 没挂，问题在那两个新增角色或更深的门禁里；咨询就挂了，那是连 1 人都没跑通。
3. **三轮都开 `--debug`**（事件不落盘，开发者视角目前只能靠它输出）。额外补**一次咨询档、不开 `--debug`**，专门确认最小界面没被调试信息污染。
4. **差异分三级**：
   - **矛盾**——两个视角互相打架（铁证）
   - **不符预期**——与事前写的清单对不上（需解释）
   - **细节差异**——记下，不追

## 一句话

三轮跑完，每个问题都能回答：这东西**能不能跑、模型收到的东西对不对、用户看到的对不对、哪儿出了问题**。
