## 一、四个跨项发现（比单个缺陷更值钱）

### ① 中文上下文问题 —— 三次同根（D-115 / D-121 / D-122）

Python 的 `\w` **含中文**（已实测：`re.match(r"\w", "是")` 为真），
因此 `\b`（词边界）在中文处**找不到边界**。

三处栽在同一根因上：

| 位置 | 表现 |
|---|---|
| 中文检索 | 词边界匹配失效 |
| 字典键名 | 键名里的密钥未脱敏 |
| 正则脱敏 | `\bsk-...` 在「我的key是sk-xxx」里匹配不上 |

**结论**：任何面向中文的匹配逻辑，**必须单独验中文场景**，
只测 ASCII 会全绿通过而线上失效。
这是本项目与其他 Python 项目最不一样的地方。

### ② 死代码会主动误导（D-118）

白名单与处理分支的**两个方向都错过**：

- 分支在、事件不在白名单 → **永不可达**，用户看不到失败原因
- 事件在白名单、无分支 → **静默门禁**，导出被拦却不告知用户

死代码不只是"没用的代码"，它让人以为某件事已经处理了。
已写成双向测试锁死：白名单内每类都有分支 + 白名单外一律无效果。

### ③ 假实现必须与真实现同宽严（D-112）

`FakeLlm` 的 `call_id` 用位置序号（违反 D-065）、脚本用尽静默回落、
`list_dir` 返回子路径——**每一处都是"比真实现宽松"**。

后果不是"不够真"，而是**基于它的测试恒真**：
上层在假环境里照跑通过，接上真适配器才炸，且失败点在上层、看不出根因。

### ④ 先查证再定罪（D-114）

本批有 **3 处候选最终不是缺陷**：

- `FakeStorage.list_dir` 对不存在目录返回空元组 → 真实实现**行为一致**且有文档
- G9 动态取证不参与静态配平 → 架构**有意如此**
- Flash 档无文择体而 G3 取证方在编制外 → 架构**有意设计的降级**

凭直觉下判断会产出误报，误报拉低整份报告的可信度。
**实测确认的问题才写进决策，查清不成立的记成"已排除"。**

## 二、本批最严重的一个缺陷（D-123）

**崩溃半行毁掉全部历史**（`journal.read_all`）

追加写不是原子的。进程被强杀（断电、OOM、Ctrl-C）时末行常只写了一半——
**这不是边缘情况，而是崩溃日志的常态**，
而断点续跑（D-027/D-082）**恰恰只在崩溃之后才会用到**。

原实现一读到半行就抛 `JSONDecodeError`，
**前 N-1 条完好记录也一并读不出来**。
架构承诺「续跑天然是安全的」——**这个承诺在最需要它的时刻失效**。

已修：坏行只丢它自己，且损坏必须留痕（静默跳过 = 把数据损坏藏起来）。

## 核心判据

**审计的主要工作量在核对承诺，不在读代码。**

7 个缺陷里 **6 个**是「文档说了什么」与「代码做了什么」的落差：

- D-133 文档声称覆盖 Windows reparse point，实际依赖运行平台的路径解析
- D-134 D-030 说「Redactor 不持有密钥」，实际片段替换留下密钥主体
- D-135 `append` 注释说「崩了也留痕」，实际没有 fsync
- D-136 `driver` 注释说「保证停得干净」，实际 flush 静默失败
- D-137 `driver` 注释担心「日志里也没有」，异常穿透时正好如此
- D-141 `winname` 注释说「必须禁分隔符」，实际没禁

**代码本身写得很好**——文档密度极高且大部分是真的。
问题集中在**少数几处承诺没兑现**，而这几处恰恰后果最严重。

## 新增判据

1. **平台相关的行为，在错误的平台上测不出来**（D-133）。
   「在 Linux 上无害」不等于「在 Windows 上无害」，
   更不等于「在 Linux 上测不出来就是没问题」。
2. **安全承诺要按最坏情况验，不能按意图验**（D-134）。
   「设计上不持有密钥」不等于「密钥不会泄漏」；中间隔着一层实现时，
   意图与效果可以完全脱节。
3. **同一类承诺要在全仓统一兑现**（D-135）。
   一条路径做到了不等于别的路径也做到了；
   横向对比同类实现，比逐个孤立审更有效。
4. **返回布尔而不说明「为什么假」，等于把诊断责任推给调用方**（D-136）；
   当调用方恰好用 `_ = ` 丢弃它时，这条路径就是纯静默失败。
5. **注释与实现不符时，先查决策原文再决定改哪一边**（D-138）。
   注释记录意图，实现记录现实，冲突时不能默认实现错。
6. **报错文案要指向用户能改的那一处**（D-140）。
   「须为正整数」在用户填了 `128k` 时是误导——
   静默回落 + 错误归因 = 用户反复重填。
7. **文档里的「必须」要逐条回验，包括看起来无关痛痒的那条**（D-141）。

# 审计第 4 批：跨模块契约（commit `ae67ff7` / `acbe065`）

## 为什么换方向

第 3 批的结论：单模块审到边际收益递减（8 项里 1 项无缺陷）。

本批改审**接口与实现之间的一致性**，因为第 2 批留了个大口子：
**真实适配器从未被逐项比对过**。D-112 当时只改了 `fakes.py`，
而且只改了返回 `Result` 的两个方法。

## 本批判据

**签名对得上不等于语义对得上。** 先用 `inspect` 机械抽签名对账（35/35 齐全，
签名层无问题），再进语义层——全部发现都出在语义层。

每项都问同一句话：**假实现这么做，真实实现也这么做吗？**

## 本批结果：4 项 2 个真缺陷

| 项 | 对象 | 结果 |
|---|---|---|
| 1 | `ports/` 十 Protocol ↔ `fakes.py` ↔ 真实适配器 | **D-142** |
| 2 | `paths.py` ↔ `state_codec.py`（D-013） | 无缺陷（兑现） |
| 3 | 门禁 G0–G13 ↔ `ErrorCode` | **D-143** |
| 4 | `registry.py` ↔ `manifest.json` | 弱缺陷（记录不改） |

## 一、D-142 · 假实现漏查权限（本批最严重）

这是**第 2 批 D-112 留下的口子**，且性质相同：

```
假.exists("../../etc/passwd")  → True          真实现 → False
假.list_dir("../../etc")       → ("x.txt",)    真实现 → ()
```

D-128/D-129 当时给 `read_text` 补过权限检查，但**只补了返回 `Result` 的方法**。
`exists`（`bool`）与 `list_dir`（`tuple`）返回裸值，被漏掉了。

**教训比缺陷本身更重要**：**补一处只补 `Result` 那类，是不完整的。**
返回裸值的便捷方法同样是契约的一部分——上层照样拿它们的返回值做判断。

**修**之后加了「对着真实 `FsStorage` 逐条比答案」的测试。
判据不是「假实现更严」，而是**两边在同一输入上给出同一答案**。

## 二、D-143 · 并行分组是第二事实源

`domain/gate.py` 的 `GATE_GROUPS` 原是**独立声明**的表，
与 `GATES[...].owners` 表达同一信息——D-055/D-008 禁止的正是这个。

三处后果：漏了 TEAM_LEAD 组（G0/G6/G12）与 G13；
注释称「组2 拆出 G13 的结构部分」而 G13 根本不在表里；
`validation.py` 曾用它做编制校验，与上面那段完全重复。

**穷举 2^5 全部 32 种编制组合实测：该段独有拦截 0 例、误拦 0 例。**
故删除，改由 `gate_groups()` 从 `owners` 推导，TEAM_LEAD 组被补回。

**为什么测试没拦住**：原断言只检查「每组是单元素、成员是已知角色」，
**从未与 `GATES` 交叉校验**。

**判据**：**断言要断言「该断言的目标」，而不是它的表面特征。**
