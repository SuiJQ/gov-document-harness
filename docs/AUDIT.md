# 零信任审计导航

本文件是审计的**依据**，不是审计报告本身。
回答"为什么现在审、审什么、怎么判"，具体结论在审计批次报告里。

## 一、为什么现在审计

**审计的性价比与代码量成正比，与"是否已交付"无关。**

当前 4299 行源码 / 2714 行测试。越往后，单个缺陷的连带修复成本越高：
一个早期架构错误会横跨十几个文件，而此时这些文件已各有调用方。

更关键的一点：**现在审的每一行都还没有调用方**。
第 6 步之后接上 LLM、检索、工具层，这些模块就有了真实依赖，
改动会从"改一个文件"变成"改一个文件 + 验证所有调用方"。

## 三、工具分工与已否决项

### 在用

| 工具 | 版本 | 查什么 | 为什么不可替代 |
|---|---|---|---|
| Ruff | 0.16.9 | 风格 + F 类静态缺陷 | F 类只有它查 |
| BasedPyright | 1.40.1 | 类型 | 实测本项目零误报 |
| **pytest-cov** | 7.1.0 | **覆盖率** | 没覆盖 = 没验证 |
| **vulture** | 2.16 | **死代码** | F401 只管未用导入，整个没人调的函数它看不到 |
| **hypothesis** | 6.168.3 | **属性测试** | 唯一能自动生成"我没想到的输入"的工具 |

### 已否决（附理由）

| 工具 | 否决理由 |
|---|---|
| **nightjar-verify** | 三条硬冲突：① 自述为"LLM 驱动形式化验证流水线"，依赖 `litellm` 会联网调模型 → 违反 D-003 断网约束；② **AGPL-3.0**，与项目 GPL-3.0 不兼容；③ 引入 litellm 等 17 个传递依赖，与"依赖越少越好"背道而驰。另：v0.1.3，成熟度存疑 |
| **pytype** | 最后版本 2024-10-11，**两年未更新**。用它交叉验证一个在积极维护的 BasedPyright，产出是噪音不是信号 |
| **pyspector** | 自称 security SAST，但本程序处理公文文本而非用户代码，**没有 SQL 注入面、反序列化面、命令注入面**（工具白名单预定义）。告警会几乎全是噪音——而**噪音在零信任审计里最危险**，会把真问题淹没 |
| **mypy / pyrefly** | 与 BasedPyright **同维度重复**。同维度第二双眼睛的边际收益接近零；真正的第二双眼睛必须来自不同维度 |

**一条判断准则**：在零信任审计里，**噪音比漏报更危险**。
漏报只是漏了一个问题；噪音会让人对工具失去信任，进而忽略真正的告警。
凡是不能明确说出"它查到了什么我们查不到的东西"的工具，一律不装。

## 四、覆盖率基线（2026-10-01）

**总计 1529 行，88%，309 测试全绿。**

### 已充分验证（100%）——不必重看

`guard.py`（路径守卫）、`redactor.py`（密钥脱敏）、`driver.py`（驱动循环）、
`event.py`、`journal` 各端口定义（`clock`/`content_pack`/`registry`/`retriever`/
`secrets`/`storage`/`user_files`）。

**这三处 100% 尤其重要**：路径守卫是安全边界，密钥脱敏是不可逆事故的闸门，
驱动循环控制退出前 flush。全部被逐行验证过。

### 待补测试（按优先级）

| 模块 | 覆盖率 | 为什么优先 |
|---|---|---|
| **`adapters/state_codec.py`** | **36%** | **最高危**。见下 |
| `adapters/fakes.py` | 77% | 假实现是测试基线，其行为偏差会误导全部测试 |
| `domain/validation.py` | 80% | 校验逻辑，绕过它等于放过编造内容 |
| `domain/tier.py` | 81% | 档位决定参与角色 |
| `kernel/projection.py` | 82% | 标准模式过滤，D-023 的落地处 |
| `app.py` | 82% | 唯一装配点，装配错误全局生效 |

### state_codec.py 为什么是最高危

覆盖率 36%，且**未覆盖的恰好是主入口**：

- `dumps` 第 58 行、`loads` 第 62–68 行——对外唯一入口
- `from_json` 第 124–136 行——反序列化主体
- `_enum` / `_task_from` / `_dcard_from` / `_field_from` / `_ref_from` / `_gate_from`
  全部辅助转换函数零覆盖

而这个文件承载 **断点续跑（D-027）**：状态存进 JSON 再读回来。
`RunState` 含 `dict[RoleId, RoleState]`、`dict[DCardFieldId, DCardField]` 这类
**带枚举键的字典**，`json.dumps` 不认、`dataclasses.asdict` 也不会转键——
必须显式写。这类手写转换错一个字段，续跑就会静默丢状态或崩在启动。

**断点续跑建立在一个从未被测试的编解码器上。**

### 死代码扫描

仅 2 处命中，均为**误报**：`fakes.py:282` 与 `retriever.py:30` 的 `query` 形参
是 Protocol 签名的一部分，必须保留。

**这说明模块划分是干净的**——没有"写了但没人调"的实质死代码。

## 五、怎么判：一个审计发现的最低要求

零信任审计的产出必须是**可验证的**，不能是"这里可能有问题"。

每条发现须回答：

1. **触发条件**——什么输入/状态下会出问题
2. **后果**——用户看到什么，或什么静默失败
3. **证据**——测试、实测输出，或明确的代码路径推理
4. **修法**——具体到文件与行为

无法回答第 3 条的，降级为"存疑"并单列，**不与已证实的缺陷混排**。
混排会让整份报告的可信度被存疑项拉低。

## 六、跨平台结论的诚实边界

当前环境为 **Linux**。以下为**静态推理，未经 Windows 实测**：

- `fsync` 在 FAT32/网络盘失败（D-101）
- `os.replace` 遇占用文件抛 `PermissionError`（D-102）
- junction 与 reparse point 的 `realpath` 解析

以下为**实测**（Linux 上按 Windows 规则验证判定逻辑）：
保留设备名、非法字符、换行行为、原子写清理路径。

需在 Windows 真机跑一遍 `tests/test_cross_platform.py` 才能升级结论。
