## 一、四个跨项发现（比单个缺陷更值钱）

### ① 中文上下文问题 —— 三次同根（D-115 / D-121 / D-122）

Python 的 `\w` **含中文**（已实测：`re.match(r"\w", "是")` 为真），
因此 `\b`（词边界）在中文处**找不到边界**。

三处栽在同一根因上：

| 位置 | 表现 |
|---|---|
| 中文检索 | 词边界匹配失效 |
| 字典键名 | 键名里的密钥未脱敏 |
| 正则脱敏 | `\bsk-...` 在「我的key是sk-xxx」里匹配不上 |

**结论**：任何面向中文的匹配逻辑，**必须单独验中文场景**，
只测 ASCII 会全绿通过而线上失效。
这是本项目与其他 Python 项目最不一样的地方。

### ② 死代码会主动误导（D-118）

白名单与处理分支的**两个方向都错过**：

- 分支在、事件不在白名单 → **永不可达**，用户看不到失败原因
- 事件在白名单、无分支 → **静默门禁**，导出被拦却不告知用户

死代码不只是"没用的代码"，它让人以为某件事已经处理了。
已写成双向测试锁死：白名单内每类都有分支 + 白名单外一律无效果。

### ③ 假实现必须与真实现同宽严（D-112）

`FakeLlm` 的 `call_id` 用位置序号（违反 D-065）、脚本用尽静默回落、
`list_dir` 返回子路径——**每一处都是"比真实现宽松"**。

后果不是"不够真"，而是**基于它的测试恒真**：
上层在假环境里照跑通过，接上真适配器才炸，且失败点在上层、看不出根因。

### ④ 先查证再定罪（D-114）

本批有 **3 处候选最终不是缺陷**：

- `FakeStorage.list_dir` 对不存在目录返回空元组 → 真实实现**行为一致**且有文档
- G9 动态取证不参与静态配平 → 架构**有意如此**
- Flash 档无文择体而 G3 取证方在编制外 → 架构**有意设计的降级**

凭直觉下判断会产出误报，误报拉低整份报告的可信度。
**实测确认的问题才写进决策，查清不成立的记成"已排除"。**

## 二、本批最严重的一个缺陷（D-123）

**崩溃半行毁掉全部历史**（`journal.read_all`）

追加写不是原子的。进程被强杀（断电、OOM、Ctrl-C）时末行常只写了一半——
**这不是边缘情况，而是崩溃日志的常态**，
而断点续跑（D-027/D-082）**恰恰只在崩溃之后才会用到**。

原实现一读到半行就抛 `JSONDecodeError`，
**前 N-1 条完好记录也一并读不出来**。
架构承诺「续跑天然是安全的」——**这个承诺在最需要它的时刻失效**。

已修：坏行只丢它自己，且损坏必须留痕（静默跳过 = 把数据损坏藏起来）。

## 四、审计方法（供后续批次复用）

1. **先查真实现再定罪** —— 假实现/投影的行为必须与真适配器逐项比对，
   差得多的地方要么是缺陷，要么是有意设计，查清再写。
2. **覆盖率只是线索，不是判据** —— `redactor.py` 审计前就是 100% 覆盖，
   仍查出 4 个缺陷。
3. **查架构原文，不查自己的记忆** —— 本批多处关键判断来自架构原文
   （§5.2 / §5.4 / §8.6 / §8.7），凭印象写测试样例反而错了两次
   （角色中文名、错误码名）。
4. **穷举优于抽样** —— 脱敏按「结构维度 × 泄漏位置」铺开；
   白名单按「所有枚举值逐个断言」铺开。
5. **测试要能抓自己** —— 本批有 3 个缺陷是**写测试时当场抓出来的**
   （`list_dir` 返回值、死分支、键名脱敏），说明测试本身也是审计手段。

## 核心判据

**审计的主要工作量在核对承诺，不在读代码。**

7 个缺陷里 **6 个**是「文档说了什么」与「代码做了什么」的落差：

- D-133 文档声称覆盖 Windows reparse point，实际依赖运行平台的路径解析
- D-134 D-030 说「Redactor 不持有密钥」，实际片段替换留下密钥主体
- D-135 `append` 注释说「崩了也留痕」，实际没有 fsync
- D-136 `driver` 注释说「保证停得干净」，实际 flush 静默失败
- D-137 `driver` 注释担心「日志里也没有」，异常穿透时正好如此
- D-141 `winname` 注释说「必须禁分隔符」，实际没禁

**代码本身写得很好**——文档密度极高且大部分是真的。
问题集中在**少数几处承诺没兑现**，而这几处恰恰后果最严重。

## 新增判据

1. **平台相关的行为，在错误的平台上测不出来**（D-133）。
   「在 Linux 上无害」不等于「在 Windows 上无害」，
   更不等于「在 Linux 上测不出来就是没问题」。
2. **安全承诺要按最坏情况验，不能按意图验**（D-134）。
   「设计上不持有密钥」不等于「密钥不会泄漏」；中间隔着一层实现时，
   意图与效果可以完全脱节。
3. **同一类承诺要在全仓统一兑现**（D-135）。
   一条路径做到了不等于别的路径也做到了；
   横向对比同类实现，比逐个孤立审更有效。
4. **返回布尔而不说明「为什么假」，等于把诊断责任推给调用方**（D-136）；
   当调用方恰好用 `_ = ` 丢弃它时，这条路径就是纯静默失败。
5. **注释与实现不符时，先查决策原文再决定改哪一边**（D-138）。
   注释记录意图，实现记录现实，冲突时不能默认实现错。
6. **报错文案要指向用户能改的那一处**（D-140）。
   「须为正整数」在用户填了 `128k` 时是误导——
   静默回落 + 错误归因 = 用户反复重填。
7. **文档里的「必须」要逐条回验，包括看起来无关痛痒的那条**（D-141）。

## 排除记录（不成立的怀疑）

- **`emit`/`stop` 的竞态窗口**：首轮测试显示 0 次拒绝，疑似有窗口。
  **重验排除**——泵线程太快，200 条在 `sleep(0.01)` 前已发完，
  是时序问题。30 轮并发实测 2038 次正确拒绝。
- **`stop(drain=False)` 丢事件**：符合文档承诺（「异常退出路径，放弃剩余」）。
- **`journal.read_all` 跳过坏行导致丢好数据**：**我的测试构造错误**——
  坏行写在中间且不带换行符，下一条事件被拼接到半行后面。
  真实崩溃场景（末行半写）下 D-123 承诺完全兑现。
- **`NUL.tar.gz` 设备名判定**：`_stem` 取最后一个点之前，正确。
- **`read_all` 的 seq 断档**：机制本身正确，由此产生的
  **D-125**（`_seq` 不从 journal 恢复）仍未解，留待第 9 步。
